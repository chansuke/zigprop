## 1. Float（f16 / f32 / f64）

### 1.1 ランク空間

float の「ランク」を、絶対値の順序と符号の交互配置で定義する。ビット列 b に対し、絶対値ビット a = b の符号を除いた部分（指数＋仮数）として:

- rank = 2a（正または +0）、rank = 2a + 1（負）

これは数値順序ではなく、**符号を交互に配置した絶対値順序**である（SF2）。同じ符号内では絶対値が rank に対して単調（非正規数→正規数→∞）。rank 0 = +0.0、rank 1 = −0.0、rank 2/3 = 最小の正/負の非正規数。shrink に必要なのは数値距離の均一さではなく整礎な単純さ順序であり、P3 の降下が指数境界で不均一な数値ステップになることは許容する（設計として明記）。f64 で a < 2^63 なので rank は u64 に収まる。f32 / f16 も同様。

### 1.2 分布（SF1: float 専用ミックス）

整数のクラスミックスをそのまま使うと、f64 ではクラス 0/2 がどちらも極小の非正規数域に集中し、通常の演算で意味のある値域を引く確率が下がる。v0.2 の float は専用の4クラスにする（いずれも2 draw、組のキー注釈は生成値のランク）:

- class 0（小さい整数）: 値リスト {−16 … 16 の整数} から index で選択。全幅で厳密に表現可能
- class 1（境界）: 値集合 V = {0, −0, 1, −1, 2, −2, 0.5, −0.5, 最大の有限数とその負値, 最小の正規数, 最小の非正規数, +∞, −∞} をその型で表現可能なものだけ残し、ランクへ変換して重複除去・整列したものから index で選択
- class 2（二進グリッド）: 値リスト {k/8 | k = −1024 … 1024}（−128 から 128 を 1/8 刻み）から index で選択。全幅で厳密に表現可能（f16 でも 128 における ulp は 1/8）
- class 3（全域）: ランク = `range(R)`（R = 2^W、f64 では番兵）。P4 の正規形はこの class 3

実装は、整数生成と「クラス draw + 値 draw + キー注釈」の骨格を共有し、クラス定義だけ型種別ごとに切り替える。

### 1.3 NaN の扱い（D6、MF3）

ランク域には NaN パターン（指数 all-ones・仮数 ≠ 0）が含まれる。全ビットパターンに対する割合は f16 で約 1/32、f32 で約 1/256、f64 で約 1/2048（v1 の「約 1/2048」は f64 の値であり訂正する）。NaN は比較が常に偽になるため性質が無関係に失敗してノイズになる。

- rank→値の変換で NaN パターンを決定的に ±∞（仮数を 0 に潰す）へ写す。再生は決定的なまま。NaN を試したい利用者はカスタム生成器で作る、と文書に明記する
- **キー注釈と P4 は「写像後の生成値のランク」を使う**（MF3）。記録される draw 自体は再生用に引いたまま保持するが、組のキーは生成値の正規ランクとする。これにより境界クラス経由の ∞ と NaN 写像経由の ∞ が同一キーになり、P4 の「現在のランク」が一意になる。テスト: 両符号・複数 NaN ペイロード・再生・P4 を覆う

### 1.4 対象外の float 型（D7）

- **f128 と f80 は v0.2 でも対象外**。f128 は絶対値ビットが 127 bit で rank が u64 に収まらず、より広い意味キー（semantic key）の設計が別途必要。f80 は表現自体にプラットフォーム依存の例外符号化（unnormal / pseudo-denormal 等）があり、表現方針の決定が先に必要。「プラットフォーム依存」だけでは理由として不十分であり、この2点を理由として明記する（NTH3）。

## 2. Tagged union

### 2.1 生成手順

1. タグ draw: `index(バリアント数)` で active なバリアントを選ぶ
2. そのバリアントのペイロードを生成する（void ペイロードは draw なし）

- 非網羅 union（土台 enum が non-exhaustive）は、enum と同じ規則で名前のあるバリアントだけを生成する
- タグは通常の index draw（キー = index）であり、組注釈は付けない。P4 の対象でもない（タグは意味的な区別であり、キー等価な横移動は不要 — MF4）

### 2.2 shrink の選好 — 主張の訂正（MF4、D9 改訂）

v1 の「宣言順が選好される」は誤りであり撤回する。受理規則（キー列の shortlex）は**まずキー数（長さ）を比べる**ため、ペイロードのキー数が少ない後方バリアントが、前方バリアントより優先されることがある（例: 前方 [0, k, k] 対 後方 void [1] では [1] が勝つ）。正確な規則は「**キー数が優先し、同数の場合にタグ index（= 宣言順）が tie-break になる**」。これは整数クラス draw の罠とは違う: タグは生成値の意味そのものであり、順序の不整合ではない。設計はこの規則をそのまま文書化し、宣言順への一般的な選好は主張しない。

### 2.3 表示

失敗値の表示は `{any}` に任せる想定だが、再帰 union の入れ子表示が Zig 0.17 の std で実際に有用な形になるかは未検証（NTH2）。M2/M3 の前提として代表的な入れ子失敗の表示テストを置く。

## 3. 再帰型

### 3.1 再帰の経路

ポインタを slice 以外対象外とする以上、Zig で合法な再帰は実質 slice 経由に限られる（`struct { kids: []const Self }`、union の slice ペイロード、等）。Self を直接のフィールドや配列要素に持つ型は Zig 自体が無限サイズとして弾く。設計はこの前提に立つ。

### 3.2 comptime 展開上限（MF1）

祖先リストを comptime で伸ばす素朴な実装は、再帰のたびに新しい特殊化を生み、**コンパイルが終わらない**。実行時チェックでは止められない。対策:

- 生成関数は comptime の祖先リストを持つが、**同じ型の出現回数に comptime 上限 K = 16** を設ける。祖先中に同じ型が K 回現れた地点では、それ以上の再帰呼び出しを含む分岐を特殊化しない（その地点は無条件に切断形で生成するコードになる）
- 型グラフの非循環部分は相異なる型の数で有界なので、特殊化の総数は有限になる。相互再帰・union 経由も同じ仕組みで止まる
- 実行時 `max_depth`（§3.4）は K 以下でなければならず、超過は `error.InvalidConfig` とする。実行時チェックは「K より手前で切る」ためだけに働く
- M3 の前提として、自己再帰・相互再帰・union 経由再帰が実際にコンパイルできることの compile テストを最初に置く（Sol も自身では Zig 0.17 のコンパイラ挙動を検証できていないと明言しており、実測で確定させる）

### 3.3 切断形の構成的定義（MF2）

「ペイロードが再帰を含まないバリアント」は誤り（`union { many: []const Node }` は空 slice で切断できるのに discard してしまう）。切断形 `cut(T)` を構成的に定義する:

- スカラー / bool / enum: 通常どおり draw で生成する（切断は再帰経路だけを止める）
- slice: 長さ 0（要素の切断可能性を問わない）
- optional: null
- 配列 [N]T: 要素の `cut(T)` を N 個（要素に切断形が存在することが必要）
- struct: 全フィールドを切断モードで生成する（各フィールドに切断形が存在することが必要）
- union: `cut(ペイロード)` が存在する最初のバリアントを選び、そのペイロードを切断モードで生成する
- どのバリアントにも切断形が存在しない union、および切断形の存在しないフィールドを持つ struct は、切断が必要な地点では `error.InvalidGeneration`（discard）

「切断形が存在する」ことの comptime 判定は、slice / optional が無条件に切断可能であるため、再帰が必ずそのどちらかを経由する合法な型では停止する（経由しない循環は Zig が無限サイズとして弾く）。スカラーフィールドは切断モードでも通常生成する、とここに固定する。

### 3.4 深さ予算と保証の範囲（MF5）

- `Limits` に `max_depth: usize = 8`（D8）を追加。有効範囲は 0..=K（K = 16、§3.2）
- 深さは GenContext が保持し、再帰の出現（祖先に現れた型の生成）に入るとき +1、抜けるときに戻す。**エラー経路でも戻す**（defer で保証）。兄弟部分木は親の深さから数える（経路ベース）。カスタム生成器が `generate` を呼ぶ場合も同じ深さ状態を共有する
- 実装注記（M3、2026-11-19）: 「再帰の出現」は名前付きコンテナ型（struct / union）の再入に限る。slice / optional / 配列は再帰を媒介するチャネルであり、それ自体の祖先への再登場を出現と数えると、深さを使った直後に要素の slice 自身が切断されてしまう。合法な型グラフの循環は必ず struct / union を通る（チャネルだけの循環は無限サイズになる）ため、この限定で再帰を取りこぼさない。comptime 展開上限（§3.2）も同じ限定で数える
- `max_depth = 0` では全ての再帰の出現が即座に切断形になる
- 保証の範囲を正確に述べる: 実行時スタックの深さは「型定義自体の静的な入れ子深さ ×（max_depth + 1）」程度で有界であり、`max_total_elements` はスタック枠を数えない。静的入れ子自体が深い型は、それだけで深いスタックを要する（型が有限である以上有界ではある）
- 再帰型の regressions は記録時の Limits（特に `max_depth`）に依存する。異なる `max_depth` で再生すると consumed 列の意味が変わり得るため、その旨を §7 側の注記として実装時に残す
- テスト: max_depth = 0、相互再帰、兄弟での深さ復元、生成エラー後の深さ復元

## 4. 検証計画（§9 の v0.2 版、事前登録）

条件は §9 と同じ枠組み（seed 0〜9、max_cases = 200、正常系対照と手書きループ比較を併記）。

- **T3 float**: f32 を（符号, 指数, 仮数）のビット分解で往復させる codec。mutant は仮数の最下位バイトを落とす。比較はビット厳密（SF3）。この mutant の数学的最小は **rank 2 = 最小の正の非正規数（2^-149）**（rank 0/1 は ±0 で仮数 0 のため pass、rank 2 は仮数下位バイト 1 で fail）。P3 の 2 の冪減算は rank = 2a + 符号 の形により k ≥ 9 の減算で仮数下位バイトを保存するので、失敗を保ったまま高位ビットを落とせる見込みがある。報告は3段に分ける: **発見 / 非正規数域（0 < |x| < 2^-126）への到達 / 厳密最小（rank 2）の達成**。成功条件（ゲート）は発見 8/10 以上 かつ 非正規数到達 8/10 以上とし、厳密最小の達成率は測定して報告する（ゲートにしない）
- **T4 union + 再帰**: JSON 風の値型 `union(enum) { int: i64, str: []const u8, list: []const Value }` の encode/decode 往復。mutant の意味論を固定する: **全ての list ノードを先頭2要素に打ち切り**、等号は構造的等号。期待最小反例は `list[int 0, int 0, int 0]`。根拠（SF4）: 失敗には要素3つ以上の list が必要。list のキーは [タグ 2, 長さ, 要素キー列…] で、要素は int が [タグ 0, ランク 0] = 2キーと最小であり、str は [タグ 1, 長さキー, バイト…] でタグ位置で負け、入れ子 list はキー数が増えて負ける。長さ 4 以上もキー数で負ける。よって上記がキー順序での一意な最小形。成功条件: 発見 8/10 以上 かつ 構造一致 8/10 以上（到達可能性は貪欲探索と予算 2000 に依存する経験的基準として置く）
- 対照: 正常系 codec が同条件で失敗しないこと

結果（2026-11-19、M4）: T3 は発見 10/10・非正規数到達 10/10（ゲート MET）に加え、厳密最小 rank 2 の達成も 10/10（shrink 評価 17〜40 回）。達成 10/10 は確認されたが、登録した設計はどの shrink 経路（境界クラスの index 降下か P3 の rank 降下か）が支配的かを分離していない。T4 は発見 10/10・構造一致 10/10（MET、評価 102〜305 回）。対照は両方 10/10 pass。詳細は verification.md 行 22。

## 5. 実装マイルストーン案

1. M1: float（§1.2 の専用分布、NaN 写像と正規化キー、f16 の変換・正規化の網羅テスト（NTH1）、メタテスト）
2. M2: tagged union（メタテスト、入れ子 union の表示テスト（NTH2））
3. M3: 再帰型。前提として compile テスト（自己・相互・union 経由）を先に置き、祖先追跡＋comptime 上限 K、切断形、深さ予算を実装（メタテスト §3.4）
4. M4: §4 の検証ターゲット実行と記録（Phase 0 と同じ作法）
5. 併走: 共有ヘルパー切り出しに対する golden replay テスト（SF5）を M1 の前に置く

形式検証: float ランク変換の単調性は Lean 拡張の候補（任意）。TLA+ はプロトコル不変なので変更なし。
